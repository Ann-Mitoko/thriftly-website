03 / Application architecture

Three code paths, one marketplace domain.

The repository holds the original marketplace experience plus a separately routed integration API and a small React client experiment.

Marketplace site

HTML / CSS / JS

Vendor discovery, filters, details, and seller submission interface.

Browser → PHP endpoints → MySQL

`get_vendors.php` reads verified vendors; `submit_vendor.php` stores new applications as pending.

Partner API

Express + MySQL

JSON API for verified vendors, product listings, and completed purchase records.

Consumer → Express routes → MySQL

`openapi.yaml` documents this server at `localhost:5000`; CORS and JSON parsing are enabled.

Client experiment

React vendor table

A compact React client demonstrates fetching and tabular rendering of vendor data.

React → fetch → vendors

Its current URL is `/api/vendors`, which does not match the Express API's `/vendors` route yet.

06 / Contract evolution

The spec got better when the consumer's real workflow became visible.

Partner questions and implementation checks shaped the contract rather than letting assumptions quietly harden into endpoints.

Initial scope

Marketplace ideas

Early requirements considered market maps, reviews, and other consumer browsing needs.

Partner review

Billing workflows

Team 5's actual screens called for supplier details, current listings, purchase confirmation, and history.

Week 8 updates

Useful fields

Added vendor description, nullable product brand, integer IDs, corrected categories, and GET purchase history.

Contract discipline

Gaps made explicit

Unbuilt operations are labelled planned; unrequested vendor filtering was removed instead of pretending it worked.

Integration context: `API_NEEDS.md` also records an earlier Pharmalink / nearby health-services concept and its unresolved contract questions. The implemented API documented here serves the confirmed Team 5 BillingSys integration.

Server-side checks

Validate, record, decrement.

Requires existing vendor and matching product, positive quantity and amount, and enough available stock. Successful confirmation generates a reference and reduces product quantity.

401 auth / 400 validation / 404 missing record

Purchase history is newest-first and filterable by vendor, product, and date range. Product name and brand reflect their current values, not a purchase-time snapshot.

Demo security: the current bearer check uses one shared placeholder token, not real user authentication or JWT validation. Keep it to local/demo use; it is not production security.
09 / Honest status

Working foundation. Clear next steps.

SecurityReplace the shared dev token

Introduce real authentication, scoped credentials, secret management, and authorization policies.

Contract parityImplement the five planned operations

Vendor/product update and delete, plus purchase lookup by ID, are documented but return 404 today.

React wiringAlign the client route

The React table fetches `/api/vendors`; the Express service exposes `/vendors` and needs matching response expectations.

History qualityAdd durable purchase snapshots

History currently joins live product name/brand and has no pagination, so old purchase details can change.

Integration testingMake contract checks repeatable

Add automated API tests for success, validation, authorization, stock changes, and database failures.

Documentation hygieneKeep notes in sync with the active server

Some deviation notes describe the older PHP API path approach; the current Express API uses REST paths.
